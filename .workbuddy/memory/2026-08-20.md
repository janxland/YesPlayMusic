## YesPlayMusic deploy:cdn 线上不更新 — 根因
- `pnpm deploy:cdn` 实际成功了：新构建已正确上传到 COS 源站 `mybox-1257251314.cos.ap-chengdu.myqcloud.com/www/music/dist/`（index.html `Cache-Control: no-cache` 生效，Last-Modified 今天）。
- 线上 `music.roginx.ink/` 是腾讯云 COS CDN 边缘节点，对 index.html 套了**固定 60 天缓存规则**（`max-age=5184000`），不遵循源站 no-cache，且 deploy 脚本**从不刷新 CDN 缓存**。
- 浏览器强制刷新只跳过本地缓存，跳不过 CDN 边缘缓存 → 一直拿旧 index.html（旧哈希 JS）。
- 处置：CDN 控制台 URL 刷新 `https://music.roginx.ink/` + `/index.html` 立即可上线；根治是把该 CDN 域名 index.html 缓存规则改为「遵循源站/不缓存」，并考虑在 deploy-cdn.js 末尾自动调 `PurgeUrlsCache`。
- 注意：deploy-cdn.js 注释里的「曾导致缓存60天」那次只修了对象元数据层，CDN 边缘层 60 天规则一直没动，本次即其生效。

## 用户二次疑问「上传位置不对？」— 已核查否定
- 证据：COS_PREFIX=`www/music/dist`，nginx 反代目标 `cos.roginx.ink/www/music/dist/index.html`，COS 源站已是最新构建 `bb7de86b`。三处路径一致，上传位置正确，与「线上没更新」无关。
- 真正的卡点：nginx 服务器侧的 CDN 边缘节点未同步旧缓存（服务器本地直连 cos.roginx.ink 已返回新 `bb7de86b`，但 nginx 反代同一 URL 仍拿到旧 `0010f2de`，且对 no-cache 请求头不响应）。多次 PurgeUrlsCache 对该节点无效。
- 治本：腾讯云 API 把 `cos.roginx.ink` 缓存规则改为 RuleCache `file "html"→NoCache` + `all→FollowOrigin`（覆盖所有走该 CDN 的 HTML）。
- 即时生效：将 `music.roginx.ink` 的 `location=/index.html` 反代目标由 CDN 域名改为 COS 裸源站 `mybox-1257251314.cos.ap-chengdu.myqcloud.com/www/music/dist/index.html`（裸源站本身 no-cache），资源仍走 cos.roginx.ink CDN。reload 后线上已更新到 `bb7de86b`、`cache-control: no-cache`。配置备份 `html_music.roginx.ink.conf.bak.*`。
- 经验：CDN 节点同步滞后是「刷新了却仍旧」的常见真因；对 nginx 反代 CDN 的场景，把 index.html 反代直接打到 COS 裸源站比依赖 CDN 规则切换更稳。
