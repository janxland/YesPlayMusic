## 修复（四）：切歌后可视化变慢（永久卡在程序化假数据）

- **现象**：刷新后首次打开可视化正常跟细节，切到下一首后画面"缓慢、平滑、不跟音乐"。
- **根因**：切歌 `_rebindToNewAudio` 走 destroy+new 全新 AV → `changeMediaElementSource` 中 `sameAudio=true` 但 Chromium 切歌后 cached track muted → `_cachedSourceFor` 判死链重建 captureStream → 新歌音轨未就绪 → AV_NOT_READY → **程序化兜底**（ProceduralFrame 假数据，0.27Hz 正弦慢呼吸）。恢复仅靠 'playing' 等事件，但切歌时事件已错过 → **永久假数据**。
- **修复**：`AudioVisual.js` `_scheduleUpgradeToRealSource` 加轮询兜底——每 500ms 重试升级真实源（最多 20 次/10s），成功即 `_procActive=false`；`_clearUpgradeWatcher` 同步清理 poll timer。
- **调试验证方式**：控制台 `window.__AV_DEBUG__ = true`，看 `[AV] frame src: 'procedural' | 'real'`，可确认是否卡假数据。
- **教训**：事件监听易错过时序；恢复类逻辑应配轮询兜底。切歌问题优先查 captureStream/cached source 生命周期，别先怀疑渲染器。

## 修复（五）：切歌后变假数据的真正根因（cached source 死链复用）

- **用户实证**：第一首 src=real 正常（captureStream 环境没问题，推翻 CORS 假说），切歌后 procedural 且上轮轮询无效。
- **真因**：Howler html5 pool 切歌**复用同一 <audio>**，src 变化后 Chromium 不会把新解码输出接到旧 captureStream track（track 显示 live&unmuted 但数据恒 0）。`_cachedSourceFor` 只检测 muted 字段 → 误判可复用 → analyzer 拿全 0 数据 → 1.2s 后降级 procedural 且**无自愈**。
- **修复**（AudioVisual.js，3 处）：
  1. `destroy()` 清理 `audio.__avSource__`（disconnect+null，不 track.stop）→ 切歌重建不碰死链；
  2. `_cachedSourceFor` 加 `__avSrc__` 记录 + `currentSrc` 比对 → src 变了强制重建；
  3. 静音检测触发 `_scheduleUpgradeToRealSource` + 轮询停止条件改为「真实分析就绪且数据正常」而非「analyzer 存在」。
- **部署**：新版本 index.dc4994b0.js 上线。
- **教训**：切歌复用 audio 元素时，track 状态字段（muted/readyState）不可信，必须比对 currentSrc 或验证实际数据。
